# RCA — Deploy run 91c64c76-477e-4d13-9842-17bf74122de0 (skali-chat-1)

## Outcome
Deploy FAILED at `deploy_k8s` / health_check. The pod never became ready; the backend process crashed on startup, nginx had no upstream (`connect() failed (111: Connection refused) ... /health`), and the rollout timed out. A failed run is never promoted, so nothing is live.

## Root cause (CONFIRMED, reproduced in eph sandbox)
The FastAPI backend crashes on import:

```
ModuleNotFoundError: No module named 'livekit'
  File "/app/backend/server.py", line 27, in <module>
    from livekit import api as lk_api
```

`backend/server.py` imports and uses LiveKit:
- line 27: `from livekit import api as lk_api`
- lines 2735, 5741, 5773: `lk_api.AccessToken(LIVEKIT_API_KEY, LIVEKIT_API_SECRET)...to_jwt()`

But the `livekit` package is **NOT present in `backend/requirements.txt`** (verified: `grep -in livekit requirements.txt` → not found). The `livekit.api` module is provided by the PyPI package **`livekit-api`**.

Note: the farm Dockerfile installs with `pip install --no-cache-dir --no-dependencies -r requirements.txt`, so `requirements.txt` must be a COMPLETE freeze — transitive deps are NOT auto-installed. `livekit-api` requires `livekit-protocol` (not currently in requirements.txt) in addition to packages already pinned.

## Verification (eph sandbox, source at /app/scratch)
1. Before fix — reproduced exactly: `python3 -c 'from livekit import api as lk_api'` → `ModuleNotFoundError: No module named 'livekit'`.
2. After `pip install livekit-api` (resolved to 1.2.1): `from livekit import api as lk_api` succeeds; `lk_api.AccessToken("k","s")` constructs; module resolves to `livekit.api`.
3. `livekit-api==1.2.1` Requires: `aiohttp` (already pinned 3.14.3), `livekit-protocol` (NEW → 1.1.27), `protobuf` (already pinned 5.29.6), `pyjwt` (already pinned 2.15.1), `types-protobuf` (type stubs only, not required at runtime).

## Fix (E1 to apply in source — `backend/requirements.txt`)
Add these pinned lines:
```
livekit-api==1.2.1
livekit-protocol==1.1.27
```
`aiohttp`, `protobuf`, and `PyJWT` are already present, so no further additions are strictly required. (`types-protobuf` is optional — type stubs only.)

### Watch item (not blocking)
Because the build uses `--no-dependencies`, production keeps the pinned `protobuf==5.29.6`. In the sandbox a plain install pulled `protobuf 7.36.2`, but the runtime path exercised (AccessToken → JWT) imported and ran fine. If a protobuf-version incompatibility surfaces at runtime with `livekit-protocol==1.1.27`, bump `protobuf` accordingly. The confirmed blocker is purely the two missing packages above.

## Next step
