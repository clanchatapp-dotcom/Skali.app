# RCA — Deploy run 63bd3ea1-ef76-4c98-b087-269eb643e3aa (skali-preview-1)

## Outcome
Deploy failed at the **pull_source / prepare-build-context** step. Never reached build, mongo, secrets, deploy, or health_check. App is NOT live (initial deploy, no prior healthy run).

## Error (verbatim)
```
pull_source: activity error (type: v3.InitialDeploy.PullSource ...):
prepare build context: read envs: read env file frontend/.env:
open /tmp/agent-env-.../app/frontend/.env: no such file or directory (PathError)
```

## Root cause
- Template: `fastapi_react_mongo_shadcn_base_image` (farm), frontend_type `cloudflare`.
- The build-context preparation reads every env file listed in `config.yaml` → `env_paths`, which for a farm app is `backend/.env` and `frontend/.env`.
- **`frontend/.env` does not exist in the source.** Reading it fails and the run aborts before any build work.
- This is a **source-level omission**, not a deployment-manifest bug.

## Why this is NOT fixable from the deployer side
`frontend/.env` is load-bearing for a farm frontend:
- The build (Dockerfile `frontend-build` stage) does `sed -i "s|...preview...emergentagent.com|${BACKEND_URL}|g" /app/.env` to inject the real backend URL into `REACT_APP_BACKEND_URL`.
- Merely removing `frontend/.env` from `env_paths` would let `pull_source` pass, but the frontend would build with **no `REACT_APP_BACKEND_URL`**, so runtime API calls resolve to `undefined/api/...` — a broken app. That is not an acceptable fix, so no manifest edit was made.

## Required fix (Code — E1 applies in source, then re-trigger deploy)
1. Create `frontend/.env` in the app source with the standard scaffold key, e.g.:
   ```
   REACT_APP_BACKEND_URL=https://<existing-preview-backend-host>.preview.emergentagent.com
   ```
   - Use the same preview backend URL the app already uses in preview so the build's `sed` pattern (`https://...preview...emergentagent.com`) matches and gets replaced with the production backend URL. Confirm the value matches whatever preview currently uses.
2. (Sanity) Confirm `backend/.env` exists too — it was not flagged, so it is presumably present.
3. Re-trigger the deploy. With `frontend/.env` present, `pull_source` will read it and the pipeline proceeds normally.

## Notes
- Eph sandbox could not be spawned (`eph_source_access_failed`) because `pull_source` failed to prepare the source archive — so the fix was diagnosed from the pipeline error, not reproduced in-pod.
- No deployment manifest was written. No `resume_pipeline` retry was fired, because re-running the same source fails identically until `frontend/.env` is added.
