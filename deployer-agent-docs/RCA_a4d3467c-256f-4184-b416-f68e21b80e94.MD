# RCA — Deploy failed: `ModuleNotFoundError: No module named 'livekit'`

**Deployment:** clan-stream-1
**Run:** a4d3467c-256f-4184-b416-f68e21b80e94 (initial, tier_0, template fastapi_react_mongo_shadcn_base_image, arm64)
**Failed step:** deploy_k8s / health_check — deployment never became ready; traffic was NOT switched, so nothing is live.

## Root cause (verified)
The backend crashes on startup. `backend/server.py` line 27 does:

```python
from livekit import api as lk_api
```

and the `livekit` package is **not present in `backend/requirements.txt`**. The image builds fine (the build step does not import anything), but at runtime uvicorn fails to import `server:app`, the backend process dies, nginx goes down, and the `/health` probe gets connection-refused until the rollout times out.

Exact runtime trace from the failed pod:
```
ModuleNotFoundError: No module named 'livekit'
  File "/app/backend/server.py", line 27, in <module>
    from livekit import api as lk_api
Backend died, shutting down nginx...
```
`livekit` is also used at `server.py:2720-2721` (`POST /api/livekit/token`).

## Reproduction + fix verification (eph sandbox, run source at /app/scratch)
- `grep -in livekit backend/requirements.txt` → **NOT FOUND** (confirmed missing).
- `python3 -c 'import livekit'` → reproduced the exact `ModuleNotFoundError: No module named 'livekit'`.
- `pip install 'livekit-api==0.8.1'` then `python3 -c 'from livekit import api as lk_api'` → **import OK** (`livekit.api`). The `livekit.api` namespace is provided by the PyPI package **`livekit-api`** (not a package literally named `livekit`).

## Fix (E1 to apply in source — `backend/requirements.txt`)
Add the LiveKit server SDK that provides `livekit.api`:
```
livekit-api==0.8.1
```

### IMPORTANT — the build installs with `--no-dependencies`
The Dockerfile installs with `pip install --no-cache-dir --no-dependencies -r /app/backend/requirements.txt`. Transitive deps are NOT auto-installed, so every runtime dependency of `livekit-api` must be listed explicitly in `requirements.txt`. In the sandbox, `livekit-api==0.8.1` pulled in:
`livekit-protocol`, `types-protobuf`, `protobuf`, `pyjwt`, `aiohttp`, `aiohappyeyeballs`, `aiosignal`, `attrs`, `frozenlist`, `idna`, `multidict`, `propcache`, `yarl`, `typing_extensions`.

Of these, already pinned in requirements.txt: aiohttp, aiohappyeyeballs, aiosignal, attrs, frozenlist, idna, multidict, propcache, yarl, typing_extensions, PyJWT, protobuf. **Missing and must be added explicitly:**
```
livekit-protocol==1.1.17
types-protobuf==4.25.0.20240417
```

### protobuf version caveat (please resolve before redeploy)
`livekit-api==0.8.1` wanted `protobuf 7.36.2`, but requirements.txt pins `protobuf==5.29.6` (required by `google-generativeai` / `google-ai-generativelanguage` / `google-genai`, which cap protobuf at 5.x). Because of `--no-dependencies` the build keeps 5.29.6. Verify `livekit-api`/`livekit-protocol` actually run against protobuf 5.29.6, OR pick a `livekit-api` version compatible with protobuf 5.x, to avoid trading this crash for a protobuf runtime incompatibility. (Do not simply bump protobuf to 7.x — that would break the google-* libraries.)
